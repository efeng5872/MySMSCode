## 1. 目标与现状

当前看门狗仅凭最后心跳是否达到 45 分钟决定是否恢复。服务实际已退出，也可能因旧心跳较新而被判为健康；独立心跳协程仍运行也不能证明短信转发任务正常。

本阶段目标是：获得合法执行机会后，按当前服务状态作出决策，去掉对已确认缺失服务的不必要等待，避免恢复覆盖用户停止，并确认实际启动结果。

现有代码还存在旧状态回写与用户停止竞争、先发送后保存结果等风险。依据是源码静态核对和 [复核报告](2026-10-02-keepalive-redesign-review.md)，尚未将全部风险通过故障注入复现。

## 2. 范围

本阶段包含：

1. 分离用户期望状态与运行观测，识别服务缺失、启动中、就绪、停止中、状态未确认和恢复受阻。
2. 统一短信、页面进入、开机/升级、系统重建和周期检查的恢复决策，保留每个入口原有业务职责。
3. 拦截旧恢复请求和迟到回执，合并并发恢复，确认服务就绪。
4. 记录恢复状态与原因，处理平台限制、权限缺失和重复通知。
5. 回归存量规则、转发与重试，升级时保留应用数据。

后续范围：

- 对仍存在但疑似卡住的服务自动强制重启、双进程守护和全链路活性探测。
- 新增短信持久化接收队列、重放协议、跨进程执行所有权和机器人端幂等协议。
- 新增云端组件、高频系统轮询、常驻唤醒锁、悬浮窗或无障碍保活权限。

本阶段不承诺短信绝不丢失、严格只送达一次或固定恢复时间上限。健康检查不得向真实机器人发送探测消息。

## 3. 状态定义

用户期望独立保存为“启用”或“停止”，心跳、诊断和自动恢复不能擅自改变。

| 运行观测 | 含义 | 处理 |
|---|---|---|
| 状态未确认 | 无当前实例的有效观测，或查询失败 | 完成本地核对，不直接标为健康或缺失 |
| 服务缺失 | 无当前实例，且无有效启动等待 | 用户期望启用并满足启动条件时请求恢复 |
| 启动中 | 已接纳启动请求，尚未收到有效回执 | 有限宽限内合并重复请求 |
| 已就绪 | 当前实例完成前台化与必需本地初始化，可接纳任务 | 保持运行，不等同于网络可达或短信送达 |
| 停止中 | 最新用户指令为停止，正在释放资源 | 拒绝旧恢复、旧回执与新自动发送 |
| 恢复受阻 | 权限、平台限制或本地失败导致未完成恢复 | 记录原因，保留用户期望，提供操作提示 |

旧数据库中的就绪记录不能直接作为当前实例证据。界面可以使用简洁业务文案，日志保留细分状态。

## 4. 功能需求：控制与恢复逻辑

### FR-01 用户意图优先

- 显式启停是改变用户期望的入口，自动恢复只能执行仍有效的启用意图。
- 每次新控制操作使旧恢复请求失效；停止持久化完成后，旧请求及旧回执不能重新开启监控。
- 恢复接纳、停止判定和诊断写入避免旧快照覆盖新状态，所有写入入口遵守同一约束。
- 停止不得被在途网络请求无限期阻塞；停止后不发起新的自动发送，已交给外部服务器的请求不能承诺撤回。

### FR-02 实例与启动等待识别

- 运行观测关联当前服务实例；新进程、新实例不继承旧实例就绪结论。
- 识别已请求启动但服务尚未登记的过渡期，避免误判正常启动为缺失。
- 启动等待有有限期限；到期无回执不报成功，也不能无限压制后续合法恢复。
- 查询不能为了确认服务存在而隐式创建服务；查询失败显示未确认，不直接等同于缺失。

### FR-03 去除缺失服务的心跳等待

- 确认服务缺失、用户期望启用、无有效启动等待或失败冷却且场景允许启动时，在当前检查流程请求恢复。
- 旧心跳距今 1 分钟、15 分钟或 45 分钟，不改变上述决策；不再因未满 45 分钟跳过恢复。
- 服务仍存在时，旧心跳只作为诊断线索，本阶段不因此强制重启。

### FR-04 合并恢复并保留业务输入

- 短信到达、页面进入、开机、覆盖升级、系统重建和周期看门狗共享恢复判定规则，保留来源用于启动资格判断和诊断。
- 对同一有效控制状态，只保留一个正在确认的恢复操作；不得因此合并或丢弃不同短信、不同重试任务。
- 就绪服务收到短信时沿用正常处理，不把每条短信变成重复的监控启动。
- 监控关闭时继续跳过自动处理；恢复不得绕过停止意图或权限要求。

### FR-05 就绪确认

- 启动 API 返回成功只记录“请求已发出”。
- 收到属于当前控制状态及当前实例的有效回执后，才记录“服务已就绪”或“恢复完成”。
- 回执前完成必需本地初始化，具备接纳任务能力；不等待全部网络转发和失败重试结束。
- 过期实例回执无效；初始化失败、平台拒绝和超时未确认分别记录。

### FR-06 有限重试与平台限制

- 保留 WorkManager 的 15 分钟周期请求间隔，不改为高频系统轮询。
- 根据触发来源及实际权限处理启动资格，不能用电池优化豁免代替所有场景判断。
- 明确平台拒绝时记录受阻，同样条件下避免紧密重复启动；暂时性失败允许有限尝试并进入冷却。
- 每个恢复回合的尝试次数、启动等待和冷却必须有界且可注入验证。设计阶段通过本地启动测量说明并确定参数，进入开发前复核；未经测量的秒数不作为恢复保证。
- 新显式启动开启新恢复回合；后台重复触发既不能绕过冷却，也不能反复重置冷却起点而永不恢复。

### FR-07 不同停止来源

- 应用内停止：建立有效停止意图、取消自动恢复安排；重新显式启用后才恢复。
- 系统活动应用面板停止：结合新的退出记录和最近显式启用记录识别当前停止意图，不直接按崩溃恢复。
- 系统设置强行停止：不绕过系统限制；用户重新打开后核对状态，存在有效停止证据时需显式启用。
- 划掉最近任务：不能仅凭此动作判定用户停止监控。
- 无退出原因数据本身不构成停止证据。已有且无法消解的用户停止证据需提示确认恢复；历史停止不能覆盖更晚的显式启用。
- Android 10 无退出诊断 API 时，使用可用用户意图和运行观测，不伪造退出原因。

### FR-08 时间与诊断

- 记录来源、观测结果、请求及实例标识、请求/就绪/失败时间和错误类别。
- 区分最后心跳、发现异常、请求恢复、确认就绪；不把心跳时间当作准确退出时刻。
- 超时和冷却不受修改日期时间影响；跨重启、跨实例计时不得未经校验直接比较。
- 休眠后心跳变旧不单独触发强制重启。日志使用用户可读本地时间。

### FR-09 业务异常边界

- 网络断开、机器人业务失败沿用失败和重试流程，不直接判定服务死亡。
- 对能够观测到的处理异常记录原因，不声称覆盖所有卡死场景。
- 恢复服务不自动重放发送结果不明的短信，不改变原号码/关键词匹配和通道选择语义。

## 5. 功能需求：界面与交互

| 编号 | 要求 |
|---|---|
| UI-01 状态表达 | 区分已停止、启动中、已就绪、恢复受阻和状态未确认；启用开关表示用户期望，不能单独证明运行 |
| UI-02 诊断信息 | 显示最近检查、恢复请求、就绪确认、受阻原因及已知退出信息；未知时间/原因明确显示未知 |
| UI-03 恢复操作 | 权限或系统限制需要用户操作时提供合适入口；点击启动建立新显式意图；页面刷新不能撤销停止 |
| UI-04 通知控制 | 持续相同受阻状态避免重复打扰；有意义变化或新回合按策略提示；权限或渠道关闭时保留应用内提示，不能视为通知已送达 |

| NFR-01 资源 | 不新增高频唤醒、双进程守护和常驻唤醒锁，恢复有界 | 配置核对、重复事件测试、同机型前后对比；未测量不宣称耗电下降 |

| NFR-04 隐私 | 日志不记录短信正文、真实 Webhook 或密钥；探测不产生真实群消息 | 日志及副作用检查 |

| NFR-07 文案 | 用户文案优先放资源文件，使用中文，本地可读时间 | 资源及真机检查 |

## 7. 验收场景

以下是需求验收标准；详细用例与命令在测试规划阶段编制。

| 场景 | 预期 | 类型 |
|---|---|---|
| 心跳刚更新后服务缺失 | 本次检查可请求恢复，不等待 45 分钟 | 自动化、真机 |
| 多入口同时恢复 | 一个有效恢复操作，各业务输入仍保留 | 自动化、集成 |
| 启动中重复检查 | 宽限内不重复启动，超时无回执不报成功 | 自动化 |
| 停止与恢复交错 | 停止后旧请求/回执不能重新启用 | 自动化、集成 |
| 停止后显式启动 | 新指令有效，旧实例结果不污染新状态 | 自动化 |
| 请求返回但初始化失败 | 显示未就绪并记录失败原因 | 自动化、集成 |
| 已就绪但断网 | 归入发送失败，不重启服务 | 自动化、真机 |
| 查询失败 | 未确认，不直接强制恢复已有服务 | 自动化 |
| 后台受限且通知关闭 | 受阻诊断及应用内提示，不循环拉起、不误报通知送达 | 自动化、真机 |
| 不同来源停止或退出 | 分别符合 FR-07，历史停止不覆盖新启用 | 自动化、真机 |
| 调时、重启、休眠 | 无时钟混用造成的重复恢复或虚假就绪 | 自动化、真机 |
| 旧版本覆盖升级 | 配置与历史保留，恢复遵守用户意图 | 集成、真机 |
| 短信与失败重试回归 | 匹配、通道选择、业务响应判定与重试无已知退化 | 单测、集成、受控人工验证 |

## 8. 五轮自问自答式需求澄清

### 第一轮：目标与时效

问：希望尽快恢复，保留 15 分钟周期是否矛盾？

答：用户确认系统允许时尽快恢复并兼顾耗电。事件入口获机会即可处理，周期只作兜底；去掉缺失服务的心跳等待，不承诺系统调度上限。

### 第二轮：停止与竞争

问：发出恢复前再读一次状态是否足够？

答：不足，读取后仍可能停止。旧请求、迟到回执和诊断回写都必须受控制状态约束，验收覆盖完整交错。

### 第三轮：健康与重启

问：服务存在或心跳更新，是否表示转发正常？

答：不能。就绪仅代表可接纳任务，业务结果独立显示；第一轮不自动强制重启在途发送，避免扩大重复或丢失窗口。

### 第四轮：入口与停止来源

问：合并恢复是否会丢短信？划掉任务是否就是用户停止？

答：控制恢复与业务输入分开合并，不丢弃不同短信。停止来源分别处理，缺少退出数据不直接判为停止，历史记录不覆盖新启用。

### 第五轮：可验证性与边界

问：为何不直接约定 1 秒恢复、固定启动超时或保证不丢短信？

答：后台调度无该保证，本阶段未引入持久化接收队列。设计阶段必须测量后确定有限参数，测试分别记录检查、请求及就绪耗时，不把目标写成已证实能力。
